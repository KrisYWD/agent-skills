# 技术前瞻报告

把一堆调研语料写成一份给**行业内技术负责人**看的前瞻报告：某项技术的门槛正在往哪儿移，每道工序上有哪些路线在推进，各自卡在哪、什么条件下会成。

体裁是锁死的，行业不限——口罩、电池、半导体、制药都能用。**市场报告、财务分析、竞品分析用不了这个 skill**，不要硬套。

## 输入

- **调研语料**（必需）：原始研究文档，越一手越好。专利文本、同行评议论文、标准原文、厂商公开资料、环评公示。
- **粗糙的原始报告**（可选）：**只当线索地图**。从它那里只取两样东西——选题范围，以及"哪些话题已经被证明值得写"。**内容、数据、结论一律回语料重挖，不继承它的结构，也不继承它的句子。**

> 这一条是整个 skill 里最容易被违反、违反了代价最大的。基于旧稿改写会继承旧稿的局限和错误，而且改着改着就变成润色，永远挖不到语料底下那层真东西。**旧稿写得越顺，越危险。**

## 步骤

### 1. 读语料，不读旧稿的结论

按可能的工序分组，把语料过一遍。多数研究文档开头有「一句话结论」——先扫这一层建立地图，再对有料的深读。

**完成判据**：能说出每道工序上分别有哪些路线在动、各自的证据强度，而且这些说法都能指到具体文件。做不到就继续读，不要开始写。

### 2. 提三版中心论点，停下来等选

中心论点是全文的塔尖：**这项技术的门槛正在从哪里移到哪里**。它决定后面一万多字怎么组织，猜错就得全部重写。

从语料里抽出**三个角度不同**的候选，每个配上支撑它的硬证据和它解释不了的东西。写完停住，等用户选一个、杂交、或者自己写一版推翻你。

**不要自己定就往下写。** 模型对中心论点的直觉在这个体裁上系统性偏弱——它倾向于选"技术自然演进"这类内生解释，而真实的驱动力常常在外部（法规改口径、专利到期、供应链清算）。

### 3. 定工序链的起点、终点与章节表

主干是**工序**，不是主题分类。按产线物理顺序排，读者翻到哪一道就是哪一道。

和用户确认两件事：链条从哪道工序开始、到哪道结束（例：树脂→出厂检验）；每章展开几条路线（3—4 条是这个体裁的舒适区，多了每条都写不透）。

一章一道工序，五到六章。章数超过七就该合并——不是所有工序都值一章。

### 4. 逐章写

每章按固定骨架走。**这个骨架不要改**，它是这个体裁读起来清楚的原因。

**① 先纠正 N 个流传很广的判断**（每条约 200—300 字）
不复述工艺流程——读者比你懂。只写「行业普遍以为 X，公开数据是 Y」。没有反直觉的东西，这一段就不写，直接进②。

**② 一流厂商这道工序做到什么程度**（约 250 字）
拿标杆当尺子。它做到哪、公开了什么、哪些关键参数至今不公开。

**③ 在研路线 3—4 条**（本章主体）
每条必须齐五要素，缺一条就说明这条路线还没查够：

| 要素 | 写什么 |
|---|---|
| 谁在做 | 具体的厂商、专利号、论文 |
| 做到什么程度 | 挂成熟度标签，见下 |
| 硬数据 | 带测试条件的数字 |
| 卡在哪 | 技术卡点还是商业卡点，说清是哪一种 |
| 什么条件下会成 | 可核验的触发条件，不是"有待观察" |

**④ 已经死过一次的路线**（约 200 字）
哪些看上去很美的路已经埋过人、死因是什么。这一段是全章最防忆的部分，不要省。

**⑤ 这道工序往哪走**（约 300 字）
锚在**可核验的时间节点**上：专利到期年、标准立项与实施日、设备是否已商品化、最新实测数据的年份。

**不要用"未来五年""接下来三年"这类笼统跨度。** 每条路线锚它自己的时钟，比统一年限诚实得多，也能被同行逐条去核。

### 5. 写摘要与收口

**摘要**：答案先行。中心论点 + 每道工序一句结论。领导只读这两页也要拿到全部判断。

**收口**：编辑部判断只在这里出现**一次**，不在每节末尾放格式块。三条判断 + 按可动手成本从低到高排的建议 + 明确不立项的清单。

### 6. 自查行文

读 [`references/prose-check.md`](references/prose-check.md)，跑里面的机械检查脚本，按五类毛病自查一遍。

### 7. 交 codex 复查

**这一步不能省。** 同一个模型看不出自己写的句子有毛病——本 skill 沉淀自的那次实践里，codex 抓到了自查两遍都没发现的真语法错误。

prompt 与调用方式在 [`references/prose-check.md`](references/prose-check.md) 末尾。逐条评估后再改，不要照单全收——它偶尔会把行业术语当成生造词。

### 8. 构建并自检

读 [`references/typeset.md`](references/typeset.md)。用 `assets/build_report.py` 构建 HTML，然后无头浏览器出 PDF 自检三项：页面尺寸是否全一致、末页是不是孤儿页、图与图注有没有拆到两页。

**完成判据**：三项全过，且构建脚本的成熟度断言通过。

## 贯穿全文的规则

### 成熟度三档

每条在研路线必须挂一个，构建期有断言拦。三档回答的是同一个问题——**你现在能不能拿到、能不能评**：

| 标签 | 含义 |
|---|---|
| `【已在售】` | 有认证或批准号，市面上买得到，可以直接询价 |
| `【仅专利论文】` | 只见于专利实施例或论文样片，买不到成品 |
| `【关键参数未公开】` | 市面上有货，但幅宽、克重、产能、报价或认证不公开，无法评估 |

**不要用「已量产 / 中试 / 实验室」那套成熟度阶梯**——它描述技术阶段，而读者要的是采购可达性，两者不是一根轴。也不要用「未上市」，中文里它首先指没上市（IPO）。

### 证据纪律

- **数字必须带测试条件**。气溶胶种类、粒径、流量、面速、有效面积、温湿度、预处理——缺一项，这个数字就不能和别的数字比。
- **不同研究的数据不可相加或横向比较**。人群不同、判据不同、分母不同的两个数放在一起，读者会自动做减法，而那个减法是错的。发现语料里有这种拼接，明确写出来"不可比"。
- **"查不到"要写成"这一轮公开检索没找到"**，不等于不存在。
- **绝不编造**。只有一个数据点就不画曲线、不推趋势、不补中间值。语料里说"未能确证"的，报告里也不能变成确证。
- **专利状态按检索日的公开数据库记录**，实际 FTO 必须逐国、逐项权利要求核。不要写"该专利已全部过期"这种全称判断。

### 读者是行业内的人

**不解释他们已经会的东西。** 这个体裁最常见的失败是写成科普：用类比讲原理（"静电就像毛衣"）、复述工艺流程、给术语加通俗解释。行业负责人读到这些会直接跳过，然后判定整篇不值得读。

正确的做法是**只写反直觉的部分**：他以为的和公开数据不一样的地方、他没注意到的时间窗口、他的供应商不会告诉他的事。

术语要解释时用**行内夹注**，浅一档小一档，紧跟术语。注文超过 30 字说明它是正文，不是注。

### 不要给读者下命令

读者是厂里的领导，不需要你告诉他该干什么。**给他收集到的信息，加上你的建议。** 大篇幅陈述事实，编辑部的判断只在收口出现一次。

### 图：默认不画

在这种数据密度下，图往往只是正文数字的另一种排版——**正文已经把每个区间都写成了具体数字，图能提供的"一眼看清"，一句话就给了**。

只有当图能提供**正文没有的关系**时才画（两个变量的交叉、一个趋势的外推）。画之前先问：这张图比它旁边那句话多说了什么？答不上来就不画。

真要画：用 matplotlib，不用 SVG（SVG 在打印时布局容易崩）。固定画布宽度等于正文列宽，否则各图缩放比不同、字号会不一致。图内只放标题和数据，来源、口径、告诫走图注。

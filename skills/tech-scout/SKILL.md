# 技术侦察

用户调用时**可以什么都不指定**。摸清他要什么，是这个 skill 的第一项工作，不是前提。

三个阶段，**各自独立 session**，靠一个文件夹交接。

| 阶段 | 干什么 | 派 subagent | 读哪份 |
|---|---|---|---|
| **一 · 学习** | 教会用户，同时摸清需求 | 否 | [`references/learning.md`](references/learning.md) |
| **二 · 探索** | grill ⇄ 派队 ⇄ 阶段报告 循环 | 是 | [`references/explore.md`](references/explore.md) |
| **三 · 报告** | 调用 `/tech-outlook` | 否 | 下方 §阶段三 |

**先看 `STATE.md`。** 文件夹已存在就从它记录的阶段接着走，不要从头开始。

---

## 为什么要拆成三个 session

**读者身份是互斥的。** 学习阶段的读者要被解释，最终报告的读者（`/tech-outlook` 明写）**不能被解释**——给行业负责人写科普，他会判定整篇不值得读。塞在一个 session 里必然牺牲一头。

**写作必须单点收口。** 多个团队独立踩过同一个坑：并行产出的片段拼不成一篇。正确做法是并行只用于检索，写作在最后一次完成。

**最终报告的输入必须是原始语料。** 拿阶段报告当输入会继承它的局限，而且改着改着就变成润色。这是上一次报告写砸的直接原因。

---

## 文件夹

**一次研究 = 工作目录下的一个文件夹，用研究主体命名。** 不要包装层，不要日期后缀（日期写在 `STATE.md` 里）。本次研究的全部东西都在这个文件夹内。

```
<主体>/                    ← 顶层，例：powder-metallurgy/、锂电隔膜/
├── STATE.md              ← 唯一入口，任何 session 先读它
│
│   ─── 以下三份跨阶段全程更新，放在根上 ───
├── unknowns.md           ← 四象限地图
├── glossary.md           ← 术语状态表，兼 digest 的 hover 定义数据源
├── resources.md          ← 行业信息源：期刊/协会/展会/数据入口/能问到人的地方
│
├── learning/             ← 阶段一
│   ├── notes-NN.md       ← 讲解留档
│   └── 学习小结.html      ← 阶段一收尾产出，压缩速查，带 hover 术语
├── rounds/NN/            ← 阶段二，一轮一个目录
│   ├── plan.md           ← 每路一行 + 对应哪几条 unknown（派前给用户过目）
│   ├── briefs/           ← 各路任务书
│   ├── sources.json      ← 引用账本
│   ├── pages/S<id>.txt   ← 抓到的页面正文，供逐字引文校验
│   ├── raw/              ← ★ subagent 原始报告。阶段三的输入是这里
│   └── digest.html       ← 阶段性报告
└── report/               ← 阶段三产出
```

`raw/` 单独分出来是有意的：**阶段三的 session 打开文件夹要一眼看出哪些是语料、哪些是被加工过的**。`digest` 只能当线索地图。

**文件夹名在学习阶段收尾时才定**——开始时用户还不知道要查什么，这正是他找这个 skill 的原因。在此之前用临时名，收尾时改名。

**命名跟随用户已有的习惯**：先看工作目录里现成的项目文件夹是中文还是英文、怎么起名，照着来，不要引入第二套风格。

⚠️ **不要建 `research/` 之类的包装层，也不要给文件夹加日期后缀。** 一个主体一个文件夹，和用户其他项目平级。

### STATE.md

```markdown
# <主题> · 当前状态
**阶段**：学习 / 探索（第 N 轮）/ 报告
**下一步**：<一句话，具体到动作>

## 已确定
能力边界 / 目标产品 / 目的 / 验收标准

## 学习路线（阶段一期间维护，用户可直接改）
| 状态 | 内容 | 备注 |
|---|---|---|
| ✅ 已讲 / ▶ 正在讲 / ⏳ 计划 / ⏸ 降级 | | 降级要写原因 |

## 未解决的 unknown（Top N）
→ 完整地图见 unknowns.md

## 各轮产出
| 轮 | 派了什么 | 产出 | 结论要点 |

## 已被推翻的说法
<防止新 session 凭 digest 复述作废结论>
```

最后一节是硬要求。上一个项目六轮里自我推翻八次，新 session 只读 digest 会把作废结论当结论。

## 贯穿三个阶段的规则

### 落地九问

每项技术都要回答。**这九问由 skill 定死，不问用户该关注哪些维度**——他不知道，这正是他来找你的原因。

| 维度 | 要回答的 |
|---|---|
| 成熟度 | **按采购可达性三档**，见下 |
| **工艺能力与良率节拍** | **"能做出来"和"能按节拍稳定量产"是两件事，分开评。**良率、节拍、工序能力 |
| 可制造性 | 这个设计好不好造？关键特性能不能识别与控制？ |
| 谁能供 | 材料、设备、耗材从谁那买——具体公司、牌号、型号 |
| 要投什么 | 新设备？改造现有？还是只换进料？ |
| 专利 | 关键专利在谁手里、到期没。**已过期的是免费技术资产** |
| 成本量级 | 相对现方案贵 1.2 倍、3 倍还是 30 倍 |
| **时间窗口** | **什么时候能用？专利哪年到期？标准哪年实施？窗口开多久？** |
| **为什么还没普及** | **它这么好为什么市面上不是它——这一栏往往最有价值** |

### 成熟度按采购可达性分三档

三档回答的是同一个问题——**你现在能不能拿到、能不能评**：

| 标签 | 含义 |
|---|---|
| `【已在售】` | 有认证或批准号，市面上买得到，可以直接询价 |
| `【仅专利论文】` | 只见于专利实施例或论文样片，买不到成品 |
| `【关键参数未公开】` | 市面上有货，但幅宽、克重、产能、报价或认证不公开，无法评估 |

⚠️ **不要用「已量产 / 中试 / 实验室」那套阶梯**——它描述技术阶段，而决策者要的是采购可达性，两者不是一根轴。`/tech-outlook` 在构建期有断言拦这个，用错了阶段三要返工。技术阶段若已知，另起一句写在硬数据里。

**不给技术打总分。** 交付的是「差多少、要做什么才能补上」，不是一个数字。评下来"现在不行"的，要补一条**成熟化路径**：需要什么条件、代价多少、多久。

⚠️ **不评估"用户自己接不接得住"**——你不了解他的现状，评了就是编。这一维留给用户自己。

### 证据纪律

- **凡写下的论文、专利、公司、型号、价格、认证号，必须实际检索到并能给出可访问 URL。** 查不到写"未检索到"。**宁可只给 3 条真的。**
- **搜不到写"未能确证"**，这是过程不是结论
- **每条标证据强度**：`[同行评议]` · `[官方]` · `[多方]` · `[单一]` · `[厂商宣称]` · `[预印本]` · `[推断]` · `[未验]`
- **性能数字带测试条件**，没有就明说没有
- **区分「厂商宣称」与「第三方验证」**
- **不同研究的数据不可相加或横向比较**。人群、判据、分母不同的两个数并列，读者会自动做减法，而那个减法是错的。发现语料里有这种拼接，明确写出"不可比"
- **不限年代**——老专利实施例里有近年综述不会重复的一手数据

📌 文字纪律会被突破（上一个项目出过 15 例以上虚构条目），所以探索阶段用 [`assets/sources.py`](assets/sources.py) 做**脚本硬校验**。见 explore.md。

### 先排除补偿

用成品级功能指标反推材料/系统内部状态之前，先问**有没有别的机制在补偿**。上一个项目撞了四次同一个陷阱。见 [`references/traps.md`](references/traps.md)。

### 被质疑先去查

用户的质疑准确率高于你的直觉。质疑来了先去测去查，不要先辩护。说错了直接改，不绕。

## 阶段三 · 报告

调用 `/tech-outlook`，输入是 `rounds/*/raw/` 的**原始语料**。

`digest.html` 只当线索地图用——**只取选题范围和"哪些话题已被证明值得写"，内容、数据、结论一律回 `raw/` 重挖**。

报告**自带失效日期**：技术成熟度评估是时点评估，公认保质期 1-6 个月，取决于技术演进速度。
